Talk 35 · Carnegie Mellon University

Misha Khodak: Automatic Architecture Design For Emerging Machine Learning Tasks

This whole series is about getting computers to predict how physical things behave by learning from examples instead of only using hand-written math. Most successful learning programs were carefully designed to work on pictures, using a trick called convolution that forces the network to look at small local patches and share what it learns across space. This talk is about how to automatically redesign these building blocks so they work on completely different problems — graphs, sequences, equations that describe change over time — without an expert having to invent new operations by hand each time.

YouTube source · Talk page

Core Problem

We have neural networks that were brilliantly tuned to see patterns in pictures by using a technique called convolution, which forces the network to notice the same small local features everywhere in the image. But real science deals with sequences (measurements over time), graphs (connected networks of things), differential equations (rules that describe how things change), and other structures that don't look like grids of pixels. For each new structure, experts have to invent new operations by hand — a slow process that only works if someone understands both the science and neural networks. Standard tools for automating network design only change which operations are plugged in, not what those operations themselves can be.

First-Principles Model

Think of a neural network architecture as a recipe that says which patterns the network can recognize. Convolutions work by making the network look at small neighborhoods and reuse what it learns across space — that forces the network to find spatially local features. The idea here is to flip this: instead of asking 'how do we wire together fixed building blocks?', ask 'what properties does the problem itself have?' — is it symmetric? Does shifting matter? Is it about neighbors being related? Then design or search for operations that bake those properties in. This turns picking an architecture into finding the right operations that match the problem, rather than inventing them by guesswork.

Key Claims

  • Neural networks designed for pictures are very good at pictures but don't transfer cleanly to sequences, graphs, or physics equations without custom operations.
  • Different problem structures need different neural operations — what works for images wastes effort on trees or time series.
  • You can design operations that keep the good properties of convolution but work on many different problem types.
  • You can automate the search for which operations to use in a network for a new problem.
  • The best choice of operations depends on both how much data you have and the structure of the problem itself.
  • Searching over both how to connect operations and what the operations can do is possible but computationally expensive.

Important Terms

Architecture Transfer

Taking successful design patterns from one problem type (like images) and adapting them to work on a different problem type (like time series) by changing the operations the network uses.

XD-Operation

A type of neural operation designed to generalize the core idea of convolution — making the network share what it learns and focus on local structure — so it works on many different problem types beyond just pictures.

Degree-of-Freedom Constraint

A built-in rule that reduces the number of tunable knobs in a network by forcing certain structure into it: for instance, making weights identical at different locations, or making the network treat neighbors the same way everywhere.

Topology Search

Automatically trying different ways to connect neural operations together — different wirings of the network — to find which arrangement learns best for a given task.

Architecture Design

The choice of which operations to use in a network and how to wire them together; this choice determines what kinds of patterns the network can learn and which patterns it misses.

Connections Across The Series

  • Earlier in this series you learned about neural architecture search as changing how operations are wired together; this talk goes deeper by asking whether the operations themselves can be designed or searched automatically.
  • It connects to the talks on graph networks, Fourier neural operators, and physics-aware solvers because all of them start with a question: what structure does the problem have, and how can we build a network that respects that structure?
  • This reinforces the central theme: the decisions you make when designing a network act like training wheels or blinders — they decide what patterns the network can catch and what it will miss, which often matters more than how much you train it.

Practical Caution

Making architecture search automatic sounds great, but the computer has no way to know what actually matters for your science unless you tell it explicitly. The search algorithm only sees one number you hand it — like 'make predictions match the true answer'. It can't care whether the predictions obey the physics, whether the model trains too slowly, or whether the answer is actually believable in the context of your field. You have to choose what success means: match the data, run fast, stay stable during training, respect physical laws, all of the above?

Takeaway

Architecture is the language the network uses to think about a problem. Automatic architecture search finds the right language to match each new problem.
