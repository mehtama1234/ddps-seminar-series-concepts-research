data-driven physical simulation

Inverse Problems And Control

Inverse problems are about working backward: you see what happened (the effect) and need to figure out what caused it (the hidden reason). Control is about picking actions now so that a physical system (a robot, a chemical reaction, a building in an earthquake) does what you want later. Both require a way to connect observations or goals back to the hidden causes or actions that produced them.

Ordinary Problem

Every day, engineers and scientists face two recurring headaches. First: you measure something (a temperature reading, a video of water flowing, sensor data from a bridge) but you don't know what actually caused it—you have to work backward to guess. Second: you want a system to behave a certain way (a drone to hover steady, a chemical process to make the right product) and you have to figure out what to do to make it happen. Both need you to reverse-engineer the system or pick the right lever to pull.

Naive Picture

The naive idea is simple: collect a bunch of examples of what happened, feed them to a learning program (millions of dials tuned by trial and error), and once it has seen enough, it can figure out backward causes or predict what actions to take—just like it learned a forward simulator.

Why It Fails

Physical systems are not simple patterns. They hide real obstacles: the equations describing how things move are intricate and brittle, measurements are noisy, computers approximate things in chunks (called discretization), the slightest change to a parameter can blow up or crash your answer (stability), and science demands you respect real-world rules. A learning program trained on examples can look right on the test data but completely fail the moment you change a number in the equations, jump to longer timescales, or ask it to stay true to a known physical law.

First-Principles Move

Here is the core idea: a forward simulator tells you what comes next—given a starting point and forces, it predicts motion. An inverse problem flips this around: given the motion you see, find the starting point or forces that explain it. Control does the same flip: given where you want to go, pick the forces or actions that get you there. Both rely on the forward simulator as the backbone but use it in reverse—either to search for causes or to plan for actions.

What Breaks Without It

If you skip this idea and just treat the problem as 'fit a pattern to the data,' you build a model that memorizes the examples in front of you but shatters when you change conditions: different equations, longer runs, new parameter ranges, tougher constraints. You get a false sense of success until the model meets the real world.

Summit Role

This theme ties together seminar talks about working backward to find hidden causes and about choosing actions to steer systems. It anchors why a naive learning approach fails for these problems and where the real difficulties hide.

Worked Example

In seismic imaging, geophysicists measure vibrations recorded by seismometers (the data) and want to infer subsurface rock properties (velocity c, density ρ). The forward problem: given the subsurface, the wave equation ∂²u/∂t² = c²∇²u predicts seismic waves. The inverse problem: given waves u_observed, find c and ρ. A naive approach trains a neural network: (seismic_record) → (velocity_field), fitting 100,000 synthetic examples. It predicts velocities quickly (0.1 sec) but misses sharp interfaces and violates the physics—the prediction doesn't satisfy the wave equation when checked. A physics-informed inverse solver uses differentiable simulation: iterate c_{n+1} = c_n - α·∂L/∂c, where L = ||u_simulated(c_n) - u_observed||² and the gradient is computed via adjoint wave equations. Five iterations (5 hours HPC) find c within 10% of truth, respecting wave physics exactly. Control is similar: given a drone with ∂x/∂t = v, ∂v/∂t = a + noise, choose thrusts a(t) to hover at (0,0). A learned controller maps (x,v) → a, but without physics it oscillates wildly. A control Lyapunov function ensures stability: design a(t) to minimize V(x,v) = x² + v² at each step.

One Level Deeper

An inverse problem is formulated as: find m (model, e.g., subsurface properties) that minimizes misfit ||F(m) - d_obs||², where F is the forward operator (wave simulation) and d_obs is data. The gradient ∂misfit/∂m is computed via the adjoint: define λ as the adjoint state satisfying ∂²λ/∂t² = c² ∇²λ + (u_sim - u_obs), integrated backward in time. Then ∂misfit/∂m = ∫_0^T λ_t ∇²u dt (for velocity). This is an all-at-once gradient requiring only one backward solve, not 1000 forward solves (which naive differentiation would cost). For control, the optimal controller minimizes a cost J = ∫(x²+u²)dt subject to ẋ=f(x,u). The Hamilton-Jacobi-Bellman equation gives the optimal value function V(x,t), and u* = -∂V/∂x. A control Lyapunov function is V(x) chosen so that -∇V·f(x,u) ≤ -ρV (exponential decay), guaranteeing stability. Gradient descent in the parameter space of a neural network controller is the same as policy gradient for reinforcement learning.

Failure Boundary

Inverse problems are ill-posed: many different models m can produce nearly the same observations F(m) ≈ d_obs due to noise, sparse measurements, or non-unique structure. A neural network inverts by memorizing correlations in training data; on test data with subtle differences, it guesses wrong. The adjoint gradient is accurate only if F is linear or if initialization is close to the true minimum; far from the solution, the gradient can point in completely wrong directions due to local minima (F is non-convex). Long time horizons in inverse problems compound this: if data spans 1000 seconds, the adjoint state is integrated 1000 times backward, and numerical error in the backward integration can corrupt gradients. For control, a naive neural network can find a policy that works in simulation but fails on a real robot due to unmodeled dynamics (friction, compliance); the controller is brittle to perturbations. If the true system is chaotic (e.g., climate modeling), no open-loop control can steer it reliably for long times—infinitesimal differences grow exponentially. If measurements are sparse or noisy, the inverse problem becomes even more non-unique, and the network learns one particular solution that is not robust to measurement error. Regularization (adding a penalty on model roughness) helps but can bias the solution toward overly smooth unphysical answers.
