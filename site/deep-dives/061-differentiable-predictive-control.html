Talk 61 · Pacific Northwest National Laboratory

Jan Drgona: Differentiable Programming For Modeling And Control Of Dynamical Systems

This whole series is about getting computers to predict how physical things behave by learning from data instead of only hand-written rules. This talk shows one way: build a control system (a program that decides what to do to keep a process running well) by first writing down a learnable model of how the physics work, then having a computer tune it by trial-and-error so the learned control law works fast without slowing down during real operation.

YouTube source · Talk page

Core Problem

Traditional control systems can respect physical laws and limits but need expensive computation at every moment. Learning-based control can adapt but demands huge amounts of data and often ignores hard limits. Real systems like building heating and power grids need control that runs fast on weak hardware, learns from small datasets, obeys both physical laws and safety limits, and doesn't go slack on the actual constraints.

First-Principles Model

Differentiable predictive control works like this: write the control rule (what to do next) as a learnable calculation built from a model of the physics—one where tiny changes in inputs create tiny changes in outputs, so you can measure how tweaking any dial affects the final answer. Keep the classical idea of model predictive control: guess what the system will do over the next few seconds, pick actions that minimize waste or harm, enforce limits. The change is that you do all the trial-and-error tuning beforehand on a computer, so when the system runs in real time, it just executes the already-learned control rule instead of solving a new math problem every instant.

Key Claims

  • Smoothly-differentiable programming gives a clear way to build control for systems that change over time.
  • Differentiable predictive control joins classical control tuning with scientific machine learning.
  • The method uses custom learnable physics models to train the control policy before it runs.
  • Hard limits on actions or states can be baked directly into the training process.
  • Real systems tested include building temperature control and electrical power grid scheduling.
  • The method can run fast and efficiently on weak hardware for deployed control systems.

Worked Example

Double integrator stabilization: trains 100 epochs under 1 min. Nested MPC unroll with 16 collocation points (parametric scenarios) + time horizon 5s. Comparison: interior-point solver ~100ms online; differentiable programming <1ms (100x speedup) with suboptimal cost gap <5%. Multi-zone building 20-state HVAC control: 30 days data (10 train/10 val/10 test). Linear model diverges after ~7 days; neural model with domain priors (dissipative envelope, bounded heat rates) stays robust >25 days.

Power grid 9-bus economic dispatch: 5 orders magnitude (10^5x) speedup for online control vs iterative solvers (minutes → microseconds). Solutions within 2-3% of interior-point optimality. Quadrotor ball tracking with Raspberry Pi microcontroller: memory <50MB vs 200MB+ for full MPC, trades learning offline (hours) for real-time deployment (<10ms per control update).

One Level Deeper

Parametric optimization via Lagrangian: min_θ E_ψ[L(u(θ, ψ), ψ)] s.t. inequality/equality constraints g(u, ψ), where u=network(θ), ψ=scenario samples. Penalties: L_total = L_obj + λ_g·max(0, g)^2 + λ_eq·|g_eq|^2 (augmented Lagrangian). Backprop through control policy network → optimizer gradients ∇_θ via chain rule through dynamics unroll and constraint satisfaction.

Inductive priors (spectral maps): parameterize weights as V_SV where V,S,U orthogonal (SVD factorization), clamp singular values σ ∈ [σ_min, σ_max] for stability (contraction). Lyapunov functions and control barrier functions learned as auxiliary networks to enforce convergence/safety.

Failure Boundary

Suboptimality gap grows with problem complexity and high-dimensional parameter space; no hard optimality guarantees like convex solvers. Requires pre-computed offline solution map—cannot adapt online if dynamics change. Unstable learning landscapes with chaotic sensitivity to weight initialization; stability margins need separate verification. For stochastic systems, sampling density in parametric space crucial; sparse regions show poor generalization. Memory still prohibitive for very large systems (100M+ network parameters); transfer learning across similar problems unexplored.

Important Terms

Differentiable Predictive Control

A way to train control policies where the controller learns using models where tiny input changes cause tiny output changes (so you can measure how each dial affects the answer) and where limits are written in the same learnable way.

Model Predictive Control

A control strategy where the system repeatedly predicts what will happen over the next short window of time, picks the best actions under that prediction, and applies them.

Offline Policy Optimization

Training a control strategy in advance using simulations or models, so it runs fast when deployed without needing to solve new math problems during real operation.

Nonlinear Constraint

A hard limit or rule (like 'power output cannot exceed 5000 watts') written using curved or bent math, not straight lines.

Control As A Service

Packaging a learned control algorithm so it can be reused across different systems or plugged into other applications.

Connections Across The Series

  • This lecture directly connects differentiable programming to the control problem, placing it within the DDPS seminar's focus on teaching how to learn physical behavior from data.
  • It bridges reinforcement learning and flow-control talks by showing how to combine learned models with classical mathematical optimization that guarantees safety.
  • It also touches digital twins because real control systems need fast, exact models tightly linked to the machines they operate.

Practical Caution

Control policies learned offline only work if your physics model is accurate and your safety constraints are hard rules, not soft nudges. Real deployment means testing against surprises and keeping a backup safety shutdown when things go unexpected.

Takeaway

The core insight: making everything smoothly-differentiable (so tiny changes lead to tiny changes) turns control design into a learning problem. But the learned controller is only as good as the physics model underneath, how strictly you enforce the constraints, and how careful you are before letting it loose in the real world.
